Mission-7 · PKI and Certificates

PKI and Certificates: Who Holds Which Key?

Why public keys need an infrastructure to be trusted, what a certificate really attests, and how it differs from symmetric encryption.

Principle

A public key alone proves nothing

Anyone can publish a key and claim to be the bank. A certificate fixes this: it binds a public key to an identity and a validity period, and an issuer signs the whole package. The chain of trust:

Root CA (in trust store)signsIntermediate CAsignsServer certificate

The PKI is this infrastructure: CAs that issue and revoke certificates, registration with domain validation, trust stores in OS and browser, and revocation via CRL and OCSP.

Role in IT security

What the PKI actually does

Solves key distributionThe main task. Symmetric keys need a secret channel; public keys may be published openly, the PKI attests whose key it is.
AuthenticationIn the TLS handshake the certificate proves the server's identity. The whole web's defense against man-in-the-middle rests on it.
Scales trustA few dozen root CAs cover millions of servers. No bilateral agreements needed.
Manages the lifecycleExpiry, serial numbers, revocation, re-issue: when a key is stolen, the PKI can invalidate it.

PKI vs. symmetric encryption

Different layers, one pipeline

PKI (asymmetric + certificates)Symmetric (e.g. AES)
NatureInfrastructure for issue/verify/revokePure encryption algorithm
KeysKey pair + certificate per participantOne shared secret
IdentityProvable via CA signatureNot provable: key possession is all
SpeedSlow (handshake, validation)Very fast, bulk data
RevocationPossible: CRL/OCSPOnly re-keying
Works with strangers?Yes: CA is the trust anchorNo: needs pre-shared secret

In practice they work together, see next slide.

Applied · TLS as the example

PKI authenticates, AES carries the data

Certificate + signatureverifyKey exchangederiveSession key (AES-GCM)

The PKI part is slow and runs once: it proves the server's identity and secures the handshake. Then a symmetric session key encrypts the bulk traffic, because it is orders of magnitude faster. Without certificates: Diffie–Hellmann alone protects against eavesdropping, but a man-in-the-middle can swap keys undetected. The certificate closes exactly this gap.

Practical · own certificate

One command, full certificate

openssl req -x509 -newkey rsa:2048 -keyout selfsigned.key -out selfsigned.crt \ -days 365 -nodes -subj "//C=DE\CN=localhost\emailAddress=student@example.com"
-newkey rsa:2048Generates the RSA key pair (key + cert in one step).
-x509 -days 365Output an X.509 certificate, valid 1 year.
-subj "CN=…"Distinguished Name: the identity the certificate attests.
Self-signedIssuer = subject, no third party confirms identity. Browser warns "Not trusted". Let's Encrypt needs a public server + ACME client (certbot) instead.

Significance for secure communication

Each component carries one guarantee

Subject/SANThe host check: the certificate is only valid for exactly this server.
Signature + chainAuthenticity: verified back to a root CA, defeats man-in-the-middle.
ValidityRejects expired or already-compromised keys.
Public keyBasis of the key exchange: only the private key holder can derive the session.
Serial + CRL/OCSPRevocation limits the damage when a key is stolen.
Key Usage, CA flagRestricts scope: a server certificate cannot sign other certificates.

The Certificate Authority (CA), which is trusted and signs, is the crucial difference.

Certificate = public key + identity + validity + CA signature
