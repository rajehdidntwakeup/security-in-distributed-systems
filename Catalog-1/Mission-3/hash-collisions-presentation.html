Mission-3 · Password Hashing

Collisions, Rainbow Tables & The Salt Defense

When you only store H(password), the maths already works against you unless you salt, pepper and slow it down.

1 · Collision

Two inputs, one hash

H(x) = H(y) with x ≠ y

Pigeonhole principle: hashing maps an infinite input space onto a fixed output space (SHA-256 → 2256 values). Collisions are therefore always possible, a good hash only makes them hard to find.

Attacker's goalFor passwords this is a preimage problem: given hash h, find any input with H(input) = h. And humans give them a tiny search space.

1 · Collision

Three ways to clash

CollisionFind any pair x, y with H(x) = H(y). Birthday attack: ~2n/2 work for an n-bit hash.
Second preimageFix y. Find x ≠ y with H(x) = H(y). Defeats signature/integrity checks on chosen documents.
PreimageGiven h, find any x with H(x) = h. Password cracking - but over trillions of human passwords, not 2256.

SHA-256 survives generic attacks - yet password hashing still breaks, because nobody's password is 256 bits of entropy.

1 · Rainbow tables

Invert hashes without brute force

A rainbow table is a precomputed data structure that recovers the plaintext for a given hash - all work done in advance. Time-memory trade-off.

Why not a plain lookup table?All passwords ≤ 8 chars over 95 printable ASCII ≈ 958 ≈ 6.6 · 1015 hashes. Storing every pair is infeasible, rainbow tables store only chain endpoints

1 · Rainbow tables

Chains & the reduction function R

p0-H→h0-R→p1-H→h1-R→… -H→hn-1-R→pn

Start from a plaintext (aaaaaa), hash it, then R deterministically folds each hash back into a new "password". Chain length e.g. 1000 - the table keeps only p0 and pn, so gigabytes shrink to megabytes.

1 · Rainbow tables

Lookup: walk the chain

01
From target hash h, apply R → H → R → … up to chain length, hoping to hit a stored endpoint pn.
02
Endpoint match → restart from its start p0 and rebuild the whole chain.
03
Every hash checked along the way; where h = H(pi) - recovered, that's the password.

Tables use several different R functions to limit chain merging. Limits: one table per hash algorithm, per character set and length, plusGlobal random value none of it works on salted hashes.

2 · Attacks

What this buys the attacker

Password theftSteal DB → lookup each unsalted hash → plaintext in seconds. Works on reused passwords in mail, VPN, anything.
Signature forgeryChosen-prefix collision: get benign m1 signed, swap in malicious m2. MD5 rogue CA (2008), SHA-1 SHAttered (2017).
Integrity bypassTampered file still passes an MD5 checksum comparison - e.g. in software update distribution.

Bonus without any cracking: two users with the same unsalted hash visibly share a password.

3 · Defense

Salting - precomputation dies

stored = H(salt ‖ password)

SaltRandom, per-password, e.g. 16 bytes, stored in plaintext next to the hash. Not secret - uniqueness is its entire job.
EffectNo duplicate hashes across users. A rainbow table per salt value per user destroys the storage advantage. Cracking falls back to guessing one hash at a time, at full cost each.

3 · Defense

Peppering - the secret that's not in the DB

stored = HMAC-SHA256(key = pepper, salt ‖ password)

PepperGlobal random value, secret, stored outside the database - env var, vault, HSM. If the attacker takes the DB alone (SQL injection, dump), guessing is impossible, not just slow.
Trade-offMust be managed; if lost, all passwords are unrecoverable
